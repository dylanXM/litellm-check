## Incident summary (from the vendor announcement)

On 2026-10-21, LiteLLM's release pipeline was compromised and v1.107.0 was pushed to PyPI and the container registries with compiled malware that steals credentials and loads remote code. Per the official announcement (https://docs.litellm.ai/blog/security-incident-oct-21-2026, last updated 2026-10-21 20:30 UTC): the PyPI release litellm==1.107.0 was live 2026-10-21 11:39:51-13:23 UTC; the Docker Hub tags v1.107.0, latest, main-latest and main-stable pointed at a compromised image index 2026-10-21 11:46:56-14:20 UTC; the same tags on GHCR were compromised 2026-10-21 11:46:56-13:51 UTC. All previous versions are stated to be safe, the impacted artifacts have been pulled, and enterprise customers on the private enterprise registry were not impacted. Every rule in this tool derives from that announcement; no third-party indicators are used.

This report lists exposure indicators found in the scanned tree, with file-and-line evidence, so the results can be handed to an engineering or security team. Read the **Detection limits** section before drawing conclusions.

## If you are affected - vendor response steps

Condensed from the announcement's "What to do if you are affected" section:

1. Do NOT start with pip install: any Python start in an affected environment runs cook.pth and sitecustomize.py again, and that includes running pip.
2. From the shell, delete cook.pth, cook.py, sitecustomize.py and any matching __pycache__/cook*.pyc and sitecustomize*.pyc from every affected site-packages.
3. Kill the detached python daemon (it holds /tmp/remote_code_loader.lock).
4. Reinstall pinned to litellm==1.106.2. Rebuilding images and venvs from scratch is better.
5. If 1.107.0 was ever installed on a host with outbound internet, assume the exfiltration succeeded; rotate everything the host could reach: the instance/task IAM role, every provider key stored in the LiteLLM proxy DB plus the master and virtual keys, the DATABASE_URL password, and any secret in the environment of any process on the host.
6. Check CloudTrail for GetCallerIdentity from the instance role around install time, then for use of the role's credentials from outside your infrastructure.

## Detection limits

This tool checks a fixed, published set of indicators taken from LiteLLM's official incident announcement: dependency specs and lockfiles that pin, admit or exclude litellm==1.107.0; container image tags and digests named in the announcement; installed litellm distribution metadata; and the implant/marker filenames the announcement lists (cook.pth, cook.py, sitecustomize.py, their compiled caches, litellm-1.107.0.dist-info, remote_code_loader.lock).

It cannot detect: installs that left no artifact in the scanned tree (environments rebuilt or deleted after exposure); images pulled and run without any definition file in the tree; exposure recorded only in CI logs, shell history or registry audit logs; files renamed away from the announced names; or compromise of secrets that were reachable from an affected host (only rotation addresses that).

Severity wording follows the announcement: findings marked critical are the artifacts the vendor says to treat as compromised; 'admits'-style findings (LL-003, LL-007) mark exposure surface whose impact depends on when an install or pull happened relative to the announced windows - they are not proof that the malicious artifact was installed.

A report without findings means only that none of the announced indicators were found in the scanned tree. Quoting the announcement: not finding an indicator 'does not prove the environment is clean'. This tool is an evidence-collection aid for the LiteLLM v1.107.0 incident; it is not a security certification, and it never declares an environment safe.
